Windows software-render black screen fix:
In software rendering (no D3D11, pixel buffer path) GetVideoWidth and
GetVideoHeight scale a large video down to fit 1920x1080. Upstream does this
with integer division (height / width * 1920). That is 0 for a video at
least 1920 wide and under 1080 high (for example 1920x800), and the width
sum is 0 for a portrait video at least 1080 high (for example 1080x1920),
so the texture is made 0 pixels high or wide and the picture is black.
Other sizes such as 1440x1080 came out wrong. The fix does the same sum with
decimals, rounds it, and never returns less than 1. Only
windows/video_output.cc is changed for this fix (it also carries one line
of the second fix and most of the third, see below). Android, iOS, macOS, Linux, ohos and
Dart sources are byte-identical to upstream.

Leftover from upstream: pubspec_overrides.yaml (pointing at ../media_kit)
is still in this folder as it came. It only applies when this package is
built on its own, not when the app depends on it, so it is left unchanged.

Windows hardware-render black picture fix (slow GPU):
In hardware rendering mpv draws each frame into one of four shared D3D11
textures, and Flutter is only ever shown a frame once the GPU has finished
it. Upstream checks that only once, without waiting, one frame later, and
throws the frame away if the GPU is not done yet. When the GPU needs longer
than one video frame per frame (a 4K film on a weak Intel iGPU such as UHD
620), that check failed every time, no frame was ever handed to Flutter, and
the picture stayed on the empty texture made at the last resize: black, while
sound and the time kept running. The fence signal was also left in the
command buffer until mpv's next flush, so it reached the GPU late.
The fix flushes right after the fence signal, and waits for the frame up to
100 ms (one reusable event, cleared before each wait, producer thread only)
before giving up on it the way upstream did. A slow GPU now shows fewer
frames instead of none. The wait runs on the shared media_kit thread pool,
so it is kept short, and it is skipped once the VideoOutput is being
destroyed so closing the player is not held up. Changed files:
windows/mailbox_swap_chain.cc, windows/mailbox_swap_chain.h,
windows/d3d11_renderer.cc, windows/d3d11_renderer.h and the one
ProducerCommit line in windows/video_output.cc (in the diff above).

+bool MailboxSwapChain::WaitForFence(ID3D11Fence* fence,
+                                    uint64_t value,
+                                    bool allow_wait) {
+  // Zangetsu patch (see ProducerCommit). Already done: no wait at all.
+  if (fence->GetCompletedValue() >= value) return true;
+  // The player is closing: behave like upstream and do not hold the shared
+  // thread pool, so the close work behind this frame runs at once.
+  if (!allow_wait) return false;
+  // The wake-up event is made once and reused; only the producer thread
+  // gets here.
+  if (!fence_event_) {
+    fence_event_ = ::CreateEventW(nullptr, FALSE, FALSE, nullptr);
+    if (!fence_event_) return false;
+  }
+  // A wait that timed out last time can leave the event set; clear it so this
+  // wait really waits for this frame (the fence is checked again below
+  // either way).
+  ::ResetEvent(fence_event_);
+  if (FAILED(fence->SetEventOnCompletion(value, fence_event_))) return false;
+  // Capped so a stuck GPU can never freeze the player: past the cap the
+  // frame is skipped exactly as upstream did.
+  ::WaitForSingleObject(fence_event_, kFenceWaitMs);
+  return fence->GetCompletedValue() >= value;
+}

Windows close-while-resizing wait fix:
Closing a player read texture_id_ while the worker thread could be in the
middle of Resize, which sets it to 0 for a moment. The close then skipped
UnregisterTexture but still waited for its callback, so it waited for ever
while holding the manager lock: no later player got a picture, and closing
the app could not finish. The same happened when no texture was ever made.
Now the worker finishes first and the ID is read there, resizing stops once
the close has started, and the wait only happens when there is a texture.
destroyed_ is atomic because several threads use it.
